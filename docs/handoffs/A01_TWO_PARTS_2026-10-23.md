## Transport investigation

The fixed first six observations compared raw sockets, Python HTTP and Windows curl against Python servers in the same and a separate process. **Windows curl 8.21.0 independently timed out after 23,360 of 24,001 bytes**, matching the previously missing 641-byte tail and prefix SHA256. The server recorded its full 24,001-byte write returning. This new reproduction bypasses OllamaProvider and Python's HTTP reader, so a cause confined to either cannot explain every observation. It does not identify the operating system, driver, filtering product, Python server or an exact root cause.

Two initial native-server controls and a later portable nine-condition validation received complete bodies. These are single timing-sensitive observations, not reliability trials or a timeout fix. Native-server response headers differ, and changing process/server/client implementations changes more than one variable. Preserve the first curl failure alongside later passes. [All observation sets](../evidence/a01-cross-client-controls-2026-10-23.json) contain byte hashes, request identity, source/binary hashes, buffers and errors. Initial source hashes describe those initial scripts, not the later portable source.

The native control uses HTTP/1.0 and explicitly sets TCP_NODELAY false to match Python's synthetic server control. Go otherwise defaults to TCP_NODELAY true, according to [the Go TCPConn documentation](https://pkg.go.dev/net#TCPConn.SetNoDelay). This test-only setting is not adopted for production and does not establish a Nagle-related cause or fix. [Microsoft's closesocket documentation](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-closesocket) also distinguishes closing and pending I/O; it is context, not diagnosis of this failure. No original provider/test reader, payload, assertion, deadline, protocol, socket option, OS or service setting was changed.

The portable observer uses only its own loopback servers, captures the existing synthetic request through deliberate pre-dispatch blocking, makes one observation per condition, and refuses an existing output path. ## Python renderer and real offline token measurements

`dc_sustainability/llm/rendering_research.py` is a functional pure-Python expansion of the pinned legacy template for one initial system message and alternating, nonempty user/assistant text. It correctly retains final-assistant versus final-user behavior, applies `/no_think` to the last user only, and preserves Unicode, whitespace, CRLF, marker-like content and template-like text as data. Unsupported tools, thinking metadata, multiple system messages, nonalternating/empty input, non-UTF-8 text, changed artifact or unapproved request settings fail explicitly. It neither launches Go nor imports a tokenizer, estimates characters, trims prompts or supplies a production callback. The provider does not import it.

The independent offline reference is the actual Go `text/template` engine in `scripts/qwen3_history_oracle.go`. Seventeen vectors were generated from that engine and byte-compared with Python. The committed golden prompts come from Go, not from the function under test. Their provenance binds the pinned template and reference source/binary. Source-text hashes normalize Git CRLF to LF; executable, template and tokenizer hashes use raw bytes. The local reference compiler was Go 1.27.3; no compiler is required by the Python renderer or ordinary tests.

The new CLI verifies local template/tokenizer SHA256 before use, imports tokenizers 0.23.3 only from an explicitly provided isolated research directory, and records actual BPE IDs/hashes.
